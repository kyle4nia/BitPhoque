# BitPhoque — Mainnet Best-Practices & Launch-Readiness Checklist

_The authoritative pre-mainnet GATE. The TN10 build is a proof-of-concept that takes
deliberate shortcuts for speed. This doc records, per the operating-baseline rule, exactly
how the mainnet version DIFFERS — so a shortcut never quietly becomes the design. NOTHING
in this list is optional for a mainnet genesis. A mainnet genesis covenant_id is FOREVER:
supply, owner, and contract cannot be changed after it lands. One mistake is irreversible
and an attacker with money and patience is actively trying to take the whole supply._

---

## TN10 shortcut  ->  Mainnet requirement (the diff)

### 1. Owner key generation  [HIGHEST SEVERITY]
- **TN10 shortcut:** key generated by `bitphoque_keygen.rs`, private hex PRINTED to a
  terminal, on a connected dev box, with the value visible in chat scrollback.
- **Mainnet requirement:** the owner key controls the ENTIRE supply — it is the single
  highest-value secret in the project. It MUST be generated AIR-GAPPED (offline machine,
  never networked), the private key MUST NEVER be printed, pasted, screenshotted, typed
  into a connected machine, or stored in plaintext. Use the project's KasSigner
  (ESP32-S3 air-gapped hardware signer) as the owner-key home.
- **HARD RULE:** the TN10 key (`dc227307...2432ce` / privkey saved locally) is TESTNET-ONLY,
  PERMANENTLY. It must NEVER become the mainnet owner key. The mainnet key is born
  air-gapped and never leaves the signer.

### 2. Signing architecture (detached / air-gapped)
- **TN10 shortcut:** harness reads the privkey (file or arg) and signs in-process.
- **Mainnet requirement:** the harness NEVER sees the private key. It builds the UNSIGNED
  tx, computes the sighash, hands ONLY the sighash to the air-gapped signer, and receives
  back ONLY the signature to attach. Same detached-signing pattern already proven in
  OracleRep's oracle signer crate — reuse that architecture for the token owner.

### 3. Verification before broadcast (accept AND reject)
- **TN10 shortcut:** dry-run, eyeball the output, broadcast.
- **Mainnet requirement:** FULL local VM verification through `TxScriptEngine` with
  `covenants_enabled` + `CovenantsContext`, BEFORE signing. AND the rejection tests must
  pass at the HARNESS level, not just the contract level:
  * a transfer that creates phoques from nothing (conservation break) MUST fail;
  * a spend with a wrong / missing owner signature MUST fail;
  * a malformed / wrong-length input MUST fail.
  The KCC20 reference suite proves the CONTRACT rejects bad input; we must prove OUR
  HARNESS does too. Accept-only is half-proven. The rejection test is the only real proof
  the gate works.

### 4. Compiler version
- **TN10 shortcut:** compiled against `tn10-toc3` silverc (pre-stable).
- **Mainnet requirement:** compile against silverscript **V1** (official release). Do NOT
  carry any contract to mainnet on the pre-stable compiler. Two upstream gates inherited
  from the OracleRep status doc are MANDATORY-PRE-V1 and apply to BitPhoque:
  * the entrypoint fixed-length-arg validation fix (pre-stable compiles a no-op length
    check — under/over-length args not validated at the entrypoint boundary);
  * the official V1 release tag itself.
  Re-baseline BitPhoque against V1 and re-run all verification once it lands.

### 5. Contract identity & supply finality
- **TN10 shortcut:** contract still self-identifies as `KCC20`; supply = 42069 placeholder.
- **Mainnet requirement:** before genesis, the contract is renamed/reviewed as `BitPhoque`
  (changes compiled bytes -> re-baseline), the supply number is FINAL (it can never change
  after genesis), and the contract has had a SECOND set of eyes / external review. A solo
  source-read is right for a no-value testnet PoC; a token holding real value warrants more
  scrutiny than one person reading the compiler once.

### 6. Funding vs ownership role separation
- **TN10 shortcut:** acceptable to self-fund (token key pays its own genesis).
- **Mainnet requirement:** keep the fee-payer (funding key) and the token owner key as
  SEPARATE roles, mirroring how a real issuance works — the entity paying tx fees is not
  necessarily the token issuer. The owner key (air-gapped) should not also be a hot
  fee-paying key.

## Mainnet launch sequence (the ceremony — none of this is done yet)

1. [ ] silverscript V1 released; BitPhoque recompiled + re-baselined against it.
2. [ ] Contract renamed to `BitPhoque`, reviewed, second set of eyes.
3. [ ] Supply number FINAL (decide before genesis; cannot change after).
4. [ ] Owner key generated AIR-GAPPED on KasSigner; pubkey extracted; privkey never leaves.
5. [ ] ctor built with the air-gapped pubkey; real redeem script + mainnet P2SH derived.
6. [ ] Genesis tx built UNSIGNED; full local VM verify PASSES; rejection tests PASS.
7. [ ] Sighash handed to air-gapped signer; signature returned; attached.
8. [ ] Dry-run reviewed; THEN broadcast to mainnet. covenant_id is now FOREVER.
9. [ ] Transfer harness proven (accept + reject) on TN10 FIRST, re-verified against V1.

## What "selling to a stranger" requires (separate milestone)
The covenant guarantees token MATH (no inflation, conservation) but NOT payment. A
trustless stranger-sale needs a SWAP COVENANT (atomic: token-release and KAS-payment both
complete or neither does) — a future BitPhoque project on the same stack, embodying the
prime directive at the trade layer (neither party can cheat the other). DEX/marketplace
listing is the liquidity-at-scale path once native-covenant-token wallet/DEX support
matures post-mainnet (June 2026 Toccata fork + emerging Kaspa DEXs). Build the swap
covenant AFTER genesis + transfer are proven.
